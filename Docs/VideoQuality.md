# 视频背景转码质量

当前配置：`CRF 14 + veryslow`，采用高画质有损编码以平衡体积。下方先保留上一轮无损验证记录，最新对比见文末。

2026-10-09，按用户要求改为 `libx264 -preset veryslow -crf 0 -pix_fmt yuv420p`，保留原始分辨率和帧率，无缩放、无音频，MP4 使用 faststart。CRF 0 是无损编码；veryslow 用于提高压缩效率。参考 [FFmpeg libx264 文档](https://www.ffmpeg.org/ffmpeg-all.html#libx264_002c-libx264rgb)。转码超时从 120 秒调整为 600 秒，避免高质量转码被原有短超时终止。

旧视频缓存会因缺少当前编码质量标记而重新生成；成功转码后写入 `video.mp4.quality`。PNG/WebP 转换参数不变。改动涉及 MediaTranscoder.swift、BackgroundMediaServiceCache.swift，以及 WineNetworkTests.swift 的旧缓存/不匹配质量/当前质量/空文件验证。

三款本机已缓存的官方背景组均从原始 WebM 重新生成无损 MP4，替换当前视频缓存。此前视频副本保留在 QAArtifacts/VideoQuality-20261009/*-previous.mp4。重新编译、运行主应用后读取新视频。

验证：三个新 MP4 均由 AVFoundation 报告 playable，并实际成功解码前十帧；使用 FFmpeg 对全部解码后的 YUV420 帧做 SHA256，三个输出均与对应 WebM 完全一致。Debug 构建/启动成功，145 项测试零失败。

此处“无损”指保留已解码的官方视频源，不会恢复视频源本身已有的压缩损失或增加原有分辨率。官方视频源为 1080p，图片为 1440p，故两者视觉锐度仍可能存在差异。编码后的文件较大，播放性能需要用户在实际机器观察；未声称视频已经比静态图更清晰。


## 画质与压缩率平衡

对绝区零完整官方视频测试了 `veryslow` 的 CRF 12/14/16，输出分别为 10,023,044 / 7,461,931 / 5,526,325 字节；相对原始视频的 SSIM 分别为 0.995257 / 0.994194 / 0.992914。综合保留细节与文件大小，当前使用 CRF 14，明显减少此前无损 CRF 0 的体积，并比最初 CRF 18 更偏重画质。SSIM 是参考指标，不代表用户主观清晰度评价。

保留原始 1080p 分辨率和帧率，未添加放大、锐化或新的第三方依赖。质量缓存标记更新为 `h264-crf14-veryslow-yuv420p-v1`，旧无损缓存会重生成。回归测试 145 项通过。

新的三款缓存分别为 9,720,234 / 10,659,049 / 7,461,931 字节，总计 27,841,214 字节（约 28 MB），相对上一轮无损版减少约 86%。三个文件均通过 AVFoundation 可播放及实际解码检查，已替换当前缓存并重启应用。


## 启动等待重叠（2026-10-09）

背景任务现在于 Wine 环境准备之前提交给 TaskScheduler，素材下载/转码与 Wine 下载、解压、共享 prefix 配置并行。两者资源锁独立，仍保留 per-game 媒体任务去重。先恢复背景模式设置，以及调度器中已存在的后台任务引用。

遮罩在 Wine 准备期间展示 Wine 阶段与进度；Wine 就绪后只等待同一批素材任务的剩余部分。素材先结束时无需再启动一轮；Wine 先结束时展示剩余素材任务计数。Wine 失败仍停留在遮罩，素材继续填充缓存，重试复用进行中任务和已有缓存。素材失败沿用原有降级行为，不把装饰素材错误当作 Wine 就绪失败。

理想总时间由串行的 Wine 耗时 + 素材耗时，变为两者耗时的较大值；实际存在共享带宽和 CPU 竞争，不承诺全部隐藏。尤其 Wine 已就绪而视频缓存缺失/失效时，仍可能等待转码。当前 CRF14/veryslow 在这台机器的完整视频试验约 50 秒，不能据此推断每台机器的耗时。
