## 任务分析约定

每项任务都区分：用户意图、任务生命周期、业务结果、成功门槛、失败恢复和终态。用户发起任务不等于动作成功。当前版本不设计 Deferred 的官方安装任务、自定义启动参数、帧率解锁或新增兼容方案。

## 1. 定位已安装游戏路径（P0）

- **用户目标**：告诉 MiPlay 现有游戏可执行文件在哪里。
- **前置条件**：用户已在系统中安装游戏，且愿意授予 MiPlay 访问所选路径的权限。
- **过程**：选择路径 → 读取路径 → 识别游戏 → 执行有效 manifest 校验。
- **成功门槛**：路径可访问、目标游戏匹配、manifest 非空且与当前版本对应、全部必需条目校验通过。此时才可将游戏视为可启动候选并进入 `Installed`。
- **失败语义**：
  - 用户取消选择：任务 `cancelled`，原路径和业务状态不变。
  - 授权失效或拒绝：任务 `failed`，不得把路径当作已接入；恢复动作是重新选择并重新授权。
  - 路径可读但文件缺失或损坏：任务可获得完整性结果 `IntegrityFailed`；游戏不得报告为已就绪。
  - manifest 缺失、为空或版本不对应：完整性结果 `IntegrityUnsupported`；不得报告通过。
- **终态**：成功、未接入、完整性损坏、无法验证或取消。不存在“已选择即已安装”。

## 2. 启动游戏（P0）

- **用户目标**：进入目标游戏画面。
- **前置条件**：目标路径已接入，完整性结果可信且通过，运行环境已就绪，目标游戏不在运行中。
- **过程**：提交启动任务 → 等待排队 → 前置校验 → 准备运行环境 → 发出进程启动请求 → 等待进程确认 → 监控运行。
- **成功门槛**：进程被确认存在并达到“可运行”判定。仅创建进程、调用系统 API 返回、任务进入 `running` 或日志出现均不算成功。
- **失败语义**：
  - 前置校验失败：启动请求没有执行，目标游戏保持原状态；先修复校验项再重试。
  - 运行环境准备失败：启动未完成，显示环境准备失败；网络或资源条件恢复后重试。
  - 进程启动失败：没有确认到可运行进程，游戏进入 `LaunchFailed`。
  - 进程超时：到达确认期限仍没有可运行进程；清理残留后进入 `LaunchFailed`。
  - 确认运行后异常退出：本次运行会话失败，游戏进入 `LaunchFailed`；不能回写为正常退出。
- **终态**：
  - 成功：任务 `completed`，游戏 `Running`；正常退出后游戏回到 `Installed`。
  - 失败：任务 `failed`，游戏 `LaunchFailed`，可查看原因并进入详情恢复。
  - 取消：只有确认无残留进程且清理完成后任务才是 `cancelled`；否则是 `failed`，提示清理未确认。

## 3. 启动失败后的恢复（P0）

- **用户目标**：知道为什么未启动，并在有依据时尝试恢复。
- **入口条件**：游戏处于 `LaunchFailed`，且保留本次失败阶段和原因。
- **过程**：查看失败事实 → 查看适用方案 → 检查资源/权限 → 确认风险 → 应用方案 → 后置验证 → 必要时自动回滚 → 重试启动。
- **完成标准**：方案应用验证通过后才可记录 `Applied`；随后重新启动并确认进程运行才算恢复了“可玩”结果。
- **终态**：`Applied`、`RolledBack`、`Failed` 或 `Unavailable`。方案 `Applied` 不等于游戏已启动，仍须单独执行启动任务。

## 4. 应用兼容方案（P0）

- **用户目标**：应用当前版本发布清单中适用于目标游戏的兼容方案。
- **前置条件**：仅允许 CS-01 或 CS-02；资源存在、目标游戏匹配、权限能力可授予、应用前状态可保存。
- **过程**：能力检查 → 保存原始快照 → 执行系统修改 → 重新读取并验证目标状态 → 保存应用记录。
- **成功门槛**：真实修改完成、后置验证通过、记录保存成功且快照可用于恢复。备份成功不是成功，命令返回不是成功。
- **验证失败**：立即尝试自动回滚。回滚后读取与原始快照一致才标记 `RolledBack`；回滚未确认时保持 `Failed` 并禁止继续应用该方案。
- **权限语义**：执行前拒绝属于 `Unavailable`；执行中授权失效属于 `Failed`，必须先自动回滚再允许重试。
- **终态**：成功 `Applied`、失败后恢复 `RolledBack`、失败且恢复未确认 `Failed`、前置条件不满足 `Unavailable`、用户取消且清理完成 `cancelled + RolledBack`。

## 5. 完整性校验（P0）

- **用户目标**：确认游戏文件是否完整、是否可以作为启动前提。
- **成功结果**：非空 manifest 与目标游戏及当前版本对应，全部必需条目存在且内容校验通过，结果为 `IntegrityPassed`。
- **损坏结果**：manifest 有效但任一必需文件缺失或内容不匹配，结果为 `IntegrityFailed`。这是可信的校验结果，不等于校验任务执行失败。
- **不支持结果**：manifest 缺失、为空、版本不对应或无法验证对应关系，结果为 `IntegrityUnsupported`。不得使用“完整”或“已就绪”。
- **执行失败**：路径不可访问、读取权限不足、I/O 错误导致无法产生上述结果，任务 `failed`；用户重新授权或重新选择路径后重试。
- **终态**：`IntegrityPassed`、`IntegrityFailed`、`IntegrityUnsupported` 或任务 `failed/cancelled`。

## 6. 版本检测与更新提示（P1）

- **用户目标**：知道本地游戏是否有官方新版本。
- **成功门槛**：成功读取并解析本地版本，同时获得官方最新版本并完成比较。
- **结果**：当前版本已是最新，或获得 `UpdateAvailable` 提示；这两者都是检测任务 `completed` 的可信结果。
- **失败语义**：网络不可用、官方服务超时、最新版本无法获得、本地版本文件缺失或解析失败，任务 `failed`。不修改既有游戏状态，不把失败当作“已是最新”。
- **恢复**：先恢复网络或修复/重新定位路径，再执行“重试检测”；达到规定自动重试上限后不循环。
- **边界**：已有 `UpdateAvailable` 时检测失败，保留此前提示并标记检测结果已过期；没有历史结果时保留当前本地业务状态，但不声称版本已确认。
- **范围**：MiPlay 只检测和提示，不执行完整官方更新包下载安装。

## 7. 运行环境准备（P0）

- **用户目标**：在无需理解 Wine 的情况下让游戏具备启动条件。
- **过程**：检测需要的运行环境 → 获取或复用版本 → 校验下载内容 → 准备环境 → 将结果交给启动任务。
- **成功门槛**：所需版本获取完成、内容校验通过、运行环境准备完成。获取请求发出或下载完成但未校验，均不能显示就绪。
- **失败恢复**：网络/来源失败时显示运行环境准备失败，用户可在网络恢复后重试；不完整或损坏的临时版本不能参与启动。
- **终态**：成功为当前 Game ID 的 `WineReady`；失败时 Task 为 `failed`，并带原因明确的 `RuntimeUnavailable`、`InstallFailed` 或 `RecoveryRequired` 业务事实；用户取消仅在清理完成后为 Task `cancelled`。失败或取消都不能显示启动成功。

> **2026-08-05 回溯口径**：本节的运行环境结果必须按当前 Game ID 解释。可用版本、已安装版本、当前选中版本和 `WineReady` 分开投影；详见 [ux-runtime-revision-2026-08-05.md](/Users/stevetan/SteveTan/Document/Xcode/MiPlay/Docs/02-ux/ux-runtime-revision-2026-08-05.md)。

## 8. TaskScheduler 任务管理（P0/P1）

| 状态 | 用户可理解的事实 | 可执行动作 | 终态规则 |
|------|----------------|-----------|---------|
| `pending` | 已接受，尚未执行 | 取消、等待 | 不能显示已完成或已应用 |
| `running` | 正在执行，阶段和当前事实可见 | 对可取消任务取消 | 只有达到任务成功门槛才到 `completed` |
| `completed` | 已得到可信的任务结果 | 查看结果、继续下一任务 | 不代表所有业务结果都是正向；结果字段必须同时提供 |
| `failed` | 请求目标未达成，或无法得到可信结果 | 按原因重试、修复前置条件、查看日志 | 目标对象不得被提升为成功状态 |
| `cancelled` | 用户取消已被接受，且必要清理/回滚已确认 | 重新提交新任务 | 取消未完成清理时不能使用此终态，改为 `failed` |

## 9. AppData 恢复、备份与迁移（P0）

- **用户目标**：在应用数据损坏或版本变化时保留可恢复信息，并知道是否可以继续使用。
- **启动读取失败**：先保留原始文件，创建只读备份副本并验证备份可读取；备份成功只表示保护动作完成，不表示数据已恢复。
- **可恢复旧备份**：提示用户“应用数据需要恢复”，展示备份时间和可能丢失的最新变更；用户确认后恢复，重新读取并校验结构，成功才进入可用状态。
- **需要迁移**：识别到旧格式但内容可读时，先备份原数据，再提示“需要迁移应用数据”；迁移成功后重新读取并校验，失败则保留原文件和备份，应用数据保持不可用。
- **无可用备份**：不得静默覆盖原文件或伪造空数据已恢复。仅在用户明确选择重新开始后，使用默认空数据；该选择必须说明会失去哪些本地配置和历史。
- **恢复失败**：终态为不可用，提供再次读取、选择备份恢复或重新开始的路径；在数据未通过读取校验前，不允许把游戏、方案历史或运行环境选择显示为已确认。

## 10. 检测可用 Wine 版本与准备运行环境（P0 / P1-UV-001 / P1-UV-002）

- **用户目标**：在设置或启动前知道 MiPlay 是否能提供可用的托管运行环境；用户不需要选择外部 Wine。
- **查询前提**：版本源策略已由 MiPlay 版本内置，用户不填写 GitHub URL、不导入系统 Wine；用户可以从预置可信镜像 allowlist 中选择一个来源，但不能输入任意镜像地址。
- **查询过程**：检查已托管版本 → 查询批准来源/批准镜像 → 校验版本身份、架构和资源 → 返回目录结果。
- **四类查询结果**：
  - `noAvailableManagedVersion`：来源请求有效，但没有符合 allowlist、架构或当前游戏需求的托管版本。文案为“没有可用的托管运行环境”，恢复为等待 MiPlay 支持版本或稍后重试，不显示“网络错误”。
  - `networkFailure`：当前选定的官方 GitHub 或预置镜像无法连接、超时、被限流或返回不可用服务。文案为“无法连接所选运行环境版本源”，恢复为检查网络后重试或主动改选其他预置来源。
  - `sourceConfigurationError`：MiPlay 内置的来源 allowlist、URL、镜像配置或版本策略无法通过配置校验。文案为“运行环境版本源配置错误”，恢复为更新 MiPlay 或等待修复，不要求用户自行改 URL。
  - **403**：选定官方 GitHub 或预置镜像明确拒绝访问时，文案为“所选运行环境版本源拒绝访问（403）”，归入来源配置/认证失败；不得显示为空目录、普通网络失败或要求用户提供 token。
  - `catalogLoading`/下载中的 `running`：正在查询或下载，不能显示“没有可用版本”或“已安装”。下载中明确说明当前目标版本和阶段。
- **镜像语义**：镜像是用户可以明确选择的批准来源。用户选择镜像后，目录查询和下载必须保留该镜像身份；不能把官方 GitHub 失败静默改写为镜像成功，也不能因镜像返回条目就跳过 artifact 校验和安装验证。
- **成功门槛**：远程目录有条目不等于版本已可用；只有 MiPlay 取得 allowlist 内 artifact、完成内容校验、安装提交、重读验证和运行环境准备后才为 `WineReady`。
- **系统 Wine 边界**：MiPlay 不检测系统 Wine、Whisky 或 CrossOver；它们不进入可用版本列表，不触发启动回退，也不能把当前 Game ID 的 `NoSelectedRuntime`、`SelectedNotReady` 或 `RuntimeUnavailable` 改成 `WineReady`。

## 11. 游戏版本、渠道与完整性证据（P1-UV-003）

- **用户目标**：理解 MiPlay 为什么能或不能确认当前游戏版本与文件完整性。
- **证据角色**：
  - `pkg_version`：仅在格式、目标游戏、安装位置和版本语义均验证后，作为本地版本候选；无法单独证明文件完整。
  - `config.ini`：仅作为渠道/来源或配置元数据候选；缺失或格式错误不能被读成“官方最新”或“完整性通过”。
  - `manifest`：完整性判断的必要依据，必须非空、与目标游戏和当前版本对应，并且全部必需条目通过。
  - 官方远程版本：只用于与可信本地版本比较，不能替代本地版本读取。
- **冲突处理**：`pkg_version` 与 `config.ini`、manifest 或远程结果互相矛盾时，文案为“无法确认当前版本”，任务失败或完整性 `IntegrityUnsupported`；不得选择一个来源静默覆盖其他来源。
- **成功门槛**：版本检测必须能说明本地版本来源和官方版本来源均可信；完整性必须能说明 manifest 身份和全部条目结果。只有 `IntegrityPassed` 才允许作为启动前提。
- **恢复**：来源缺失或格式不明时，重新授权/重新定位路径、更新到受支持版本或稍后重试；MiPlay 不把解析失败当作“当前最新”。

## 12. 重启边界与 stale bookmark 恢复（P0/P1 / P1-REV-003 / P1-REV-004）

- **持久 Running 无活动进程**：应用重启扫描发现持久 `Running`，但没有可信活动进程时，先显示“上次游戏状态未完成同步，正在恢复”，建立 `recoveryRequired` 事实；在恢复记录提交并重读验证前，不显示正常退出、可启动或新的启动重试。
- **恢复成功**：再次确认进程已退出，提交预期 Game 终态并清除恢复记录；用户随后发起的启动是新的 UserIntent/Task，不自动重放上一次启动。
- **恢复提交失败**：显示“游戏状态恢复未完成，暂时不能启动”，保留同目标保护；不得因为应用重新打开就把状态改为 `Installed`。
- **stale bookmark**：显示“正在刷新游戏路径授权”，刷新候选必须在有效 scope 内生成并写回；写回和重读成功后，消费者才可继续。
- **stale 写回失败**：显示“路径授权已刷新但尚未保存，本次操作未完成”，恢复动作是重试保存或重新选择路径；不得发布完整性、版本检测或启动成功。
- **适用消费者**：定位、完整性校验、版本检测、启动前校验和启动编排共享同一门槛，不能有消费者只使用内存中的 resolved path。

## 13. Accessibility Tree 语义任务（P1-UV-006）

- **游戏卡片**：一个可激活对象必须同时提供游戏名、动作（切换到该游戏）、选中状态、业务状态和当前可用下一步。状态圆点、背景颜色和 hover 不单独成为事实来源。
- **启动阶段与进度**：可读对象必须提供目标游戏、任务类型、当前 phase、`pending/running` 状态和真实 progress；进程确认、权限读取、后置验证、回滚验证等不可估算阶段使用“进度未知”，不读出猜测百分比。
- **错误与恢复**：可读对象必须按“目标 → 阶段 → 事实 → 副作用 → 终态 → 恢复动作”提供信息。`recoveryRequired` 必须说明当前不能重试；`Applied` 必须说明游戏尚未启动；`RolledBack` 必须说明应用未成功但原状态已恢复。
- **设置版本目录**：版本源查询中提供“正在检查版本源”；合法空目录提供“没有可用托管版本”；网络、配置和下载中分别提供对应状态，不把空列表或 spinner 推断为同一状态。
