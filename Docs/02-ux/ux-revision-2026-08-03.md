## 1. 修订边界

本稿落实以下已经冻结的产品事实：

- MiPlay 只使用 MiPlay 托管的 Wine。默认来源是官方 GitHub；用户只能从预置可信镜像 allowlist 中选择，不能输入任意 URL。
- MiPlay 不检测、不导入、不复用系统 Wine、Whisky 或 CrossOver Wine。
- 三款固定游戏分别拥有自己的 Game ID、路径、metadata、配置、背景组选择和高级配置投影。切换游戏不会继承、覆盖或合并另一款游戏的设置。
- `config.ini` 以原始 section/key/value 展示。展示字段的存在不代表字段含义已经被 MiPlay 解释或验证。
- 六项高级配置属于当前版本目标，但本轮可以 Deferred。Deferred 只能展示名称、适用性和当前状态，不能伪装成可执行能力。
- TaskScheduler 仍只有 `pending`、`running`、`completed`、`failed`、`cancelled`。本稿使用的 `recoveryRequired`、`deferred`、`unavailable`、来源结果和媒体结果均为业务事实或 UX 投影，不是新增 Task 状态。
- Research 中观察到的旧实现、API 可达、asset 直链或镜像候选只是证据，不是 MiPlay 的成功语义；本稿不复制请求发出即完成、空结果即成功或未经确认的自动回退行为。

### 1.1 统一成功口径

用户点击、意图被接受、任务进入 `pending`、执行请求发出、外部动作完成、后置验证通过是不同事实。以下词语只有在对应门槛满足后才能使用：

| 用户看到的事实 | 成功门槛 | 不得替代它的事实 |
|---|---|---|
| 游戏已启动 / `Running` | 进程被创建、健康状态达到启动判定，并且 Game 状态提交成功 | 点击启动、任务 `running`、进程创建、Wine 就绪 |
| 方案已应用 / `Applied` | 真实修改完成、后置读回验证通过、记录保存成功 | 用户点击、任务入队、备份成功、命令返回 |
| 完整性通过 / `IntegrityPassed` | 非空、版本对应的 manifest 全部条目验证通过 | `pkg_version` 存在、`config.ini` 有版本、可执行文件存在 |
| Wine 已就绪 / `WineReady` | 托管 artifact 通过来源/内容验证，安装提交和环境准备均完成并可重读确认 | API 返回版本、下载完成、解压完成、`wine --version` 有输出 |
| 背景组已切换 | 目标组的有效素材验证成功，选择持久化提交并重读成功 | 用户点选、目标 URL 存在、图片开始加载 |

所有反馈必须同时回答：**哪个对象、在哪个阶段、当前是否改变目标、现在能做什么、最终状态是什么**。

## 2. 设置页信息模型

设置页的层级只表达信息归属，不把不同游戏的配置抽象为一套共享业务规则。每一层有独立的读取状态、保存状态和错误恢复。

```text
Settings
├─ 通用
│  ├─ 应用语言
│  ├─ AppData 状态：读取、备份、迁移、恢复或重新开始
│  └─ 日志导出
├─ Wine 运行环境
│  ├─ 当前托管版本
│  ├─ 来源：官方 GitHub / 预置可信镜像
│  ├─ 可用版本目录
│  └─ 下载、校验、安装和就绪状态
├─ 原神（Game ID 独立）
│  ├─ 基本信息与游戏状态
│  ├─ 游戏路径与授权
│  ├─ 原始 config.ini
│  ├─ 完整性与版本证据
│  ├─ 兼容性方案
│  ├─ 性能选项
│  ├─ 六项高级配置状态
│  └─ 背景组
├─ 崩坏：星穹铁道（Game ID 独立）
│  └─ 同样的入口名称，但只读写星穹铁道自己的事实
└─ 绝区零（Game ID 独立）
   └─ 同样的入口名称，但只读写绝区零自己的事实
```

### 2.1 通用设置

通用设置不包含任何一个游戏的 `config.ini` 字段、路径、背景组或高级选项。

| 信息 | 空 | 加载中 | 成功 | 失败 | 不可用 |
|---|---|---|---|---|---|
| 应用语言 | 尚未选择，使用首次初始化流程 | 正在保存语言选择 | “语言已更新” | “语言更新失败，保留原语言” | AppData 未恢复，不能确认原选择 |
| AppData | 首次初始化，无历史数据 | 正在读取/迁移/恢复 | “应用数据已读取并验证” | “应用数据无法读取”并给恢复动作 | 无可验证文件或备份；只能恢复、重新开始或退出 |
| 日志导出 | 没有可导出记录 | 正在生成导出文件 | “日志已导出” | “日志导出失败” | 没有记录或导出权限不可用 |

AppData 损坏、备份和迁移的恢复必须保留原文件和诊断副本。读取 `.bak` 后仍要重新读取和验证；“发现备份”不是“已恢复”。用户选择重新开始时必须明确说明本地配置和历史可能丢失，且不删除游戏文件。

### 2.2 Wine 设置

Wine 是跨游戏的运行环境设置，但“当前 Wine 是否适用于目标游戏”仍由目标 Game ID 的启动前置条件确认。Wine 设置不得出现系统 Wine 的导入入口或检测结果。

用户选择来源的流程：

1. 默认选中官方 GitHub，并显示当前选中的来源身份。
2. 用户可以主动改选预置 allowlist 中的一个镜像。镜像名称、来源身份和支持的资源范围必须可读。
3. 用户不能输入 URL，也不能把系统已有 Wine 设为当前版本。
4. 来源切换只改变后续目录查询/下载的选定来源；不能静默把一次官方来源失败改写成镜像成功。
5. 选择提交后先查询目录，再由用户选择版本；目录成功不等于已下载或已就绪。

Wine 设置的空/加载/成功/失败/不可用语义见第 4 节。选定来源的错误必须保留来源身份，避免用户把官方 GitHub 的失败误认为镜像失败，反之亦然。

### 2.3 每款游戏的独立设置

每一个 Game ID 都有独立的设置入口和独立保存边界。三款游戏当前均可进入设置，即使该游戏路径尚未定位或 metadata 暂不可读；此时显示该游戏自己的空/不可用状态，不隐藏入口，也不借用另一款游戏的结果。

每个游戏入口按以下任务顺序组织：

1. **基本信息**：中英文名称、游戏状态、路径状态、最近一次可信版本/完整性结果。
2. **路径与权限**：选择可执行文件、重新授权 stale bookmark、处理权限拒绝。
3. **Metadata**：原始 `config.ini` 和本地版本/完整性证据，带来源、读取时间和可确认性。
4. **兼容性方案**：当前游戏适用的发布清单方案及其应用、验证、回滚结果。
5. **性能选项**：只显示该游戏的选项状态；失败后的恢复仍回到该游戏详情上下文。
6. **高级配置**：六项 A-01 至 A-06 的 per-game 状态。Deferred 不提供可执行动作。
7. **背景组**：只切换当前游戏的有效背景组。

“当前游戏”是所有这些操作的显式目标。离开页面、切换游戏或重新打开设置不会改变操作目标；任何异步结果回来后仍必须按原 Game ID 归属。

## 3. 游戏 Metadata 信息模型

### 3.1 基本信息行

基本信息区域至少提供以下语义行。中文名和英文名合并在同一行，但两种名称仍是两个可读字段，不用其中一个替代另一个：

| 行 | 展示规则 | 来源与边界 |
|---|---|---|
| 游戏名称 | `中文名 / English name` | 来自 MiPlay 固定 Game 注册信息；不随 `config.ini` 推断 |
| `game_version` | 保留原始 key 和 value | `config.ini [General]` 原始字段；可作为客户端版本证据候选，不能单独证明完整性 |
| `channel` | 保留原始数字/字符串 | `config.ini` 原始字段；不映射为“国服/国际服”等友好含义 |
| `cps` | 保留原始 value | `config.ini` 原始字段；不擅自解释为某个发行商或推广渠道 |
| `sub_channel` | 保留原始数字/字符串 | `config.ini` 原始字段；不由 `channel` 单独推断地区 |
| `sdk_version`（存在时） | 作为原始字段显示 | 只说明字段存在和值；不推断 SDK 兼容性 |
| `Audio_<language>_pkg_version`（存在时） | 按原始 key/value 显示 | 说明为音频包 metadata 候选，不显示为游戏客户端版本 |
| 其他已读取字段 | 逐项保留原始 section/key/value | 无已核实语义的字段不改名、不合并、不生成友好标签 |

`wpf_version` 没有已确认的本地语义证据；如果原始文件存在，只能按未知 key/value 展示，不能解释为 Wine、Windows 或游戏版本。

### 3.2 Metadata 来源标签与状态

每行或每组 metadata 必须能回答“从哪里读到、何时读到、是否可确认”。来源至少区分 `config.ini`、`pkg_version`、完整性 manifest 和官方版本查询；不把多个来源拼成一个无来源的“版本”。

| 状态 | 用户文案 | 用户动作 | 终态定义 |
|---|---|---|---|
| 空 | “尚未读取游戏 metadata” | 定位路径后读取/重试 | 没有形成证据，不改变 Game 状态 |
| 加载中 | “正在读取{游戏名} metadata” | 等待；可取消的读取可取消 | 读取任务仍为 `running` |
| 成功 | “已读取原始配置字段” | 查看来源、时间和原始值 | 只代表读取成功；版本/完整性须分别读取结果 |
| 缺失字段 | “未找到{key}，不是读取失败” | 查看其他来源或重试 | 该字段没有值，不填默认值 |
| 文件不可读/权限失败 | “无法读取{游戏名} metadata：需要重新授权” | 重新授权或重新选择路径 | 任务 `failed`；保留上一次可信结果，不发布新结果 |
| 解析失败 | “metadata 格式无法识别” | 重试；检查原始文件/导出日志 | 不产生版本或完整性结论 |
| 冲突/过期 | “metadata 来源不一致，暂时无法确认” | 重新校验或等待官方查询 | 不显示 `current`、`IntegrityPassed` 或 `Running` 的新结论 |
| 不可用 | “当前路径没有可确认的 metadata” | 定位正确安装路径或查看日志 | Game 可保留原状态，但本次读取无结果 |

`pkg_version` 可以在格式和目标关联均通过时提供本地版本候选；它不能替代非空且版本对应的 manifest。`config.ini` 只能提供原始配置/渠道候选；它不能单独证明最新版本、渠道友好名称或文件完整。

### 3.3 版本检测与完整性校验

版本检测和完整性校验是两个任务。版本检测比较可信的本地候选与官方最新版本；完整性校验只在取得非空、与目标版本对应的 manifest 后执行。一次任务 `completed` 仍必须带独立业务结果，不能用通用“已完成”替代。

| 场景 | 用户文案 | 恢复动作 | 终态定义 |
|---|---|---|---|
| 尚未检测 | “尚未检查{游戏名}版本” | 开始版本检测 | 没有当前版本结论 |
| 版本检测中 | “正在检查{游戏名}版本” | 等待或取消 | Task `running` |
| 已是最新 | “已确认{游戏名}为当前版本” | 继续启动/查看详情 | VersionCheck `completed + current` |
| 有新版本 | “已确认{游戏名}有新版本可用” | 使用官方更新流程；MiPlay 不执行完整更新 | VersionCheck `completed + updateAvailable` |
| 版本检测失败 | “版本检测失败，未改变现有游戏状态” | 检查网络、重新授权或重新选择路径后重试 | Task `failed`；保留上一次可信结果 |
| 无法比较 | “无法确认当前版本，缺少可验证来源” | 先补足本地或官方来源后重试 | Task `failed` 或 `unknown`；不显示最新/需更新 |
| 尚未校验完整性 | “尚未检查{游戏名}文件完整性” | 开始完整性校验 | 没有完整性结论 |
| 完整性校验中 | “正在校验{游戏名}文件” | 等待或取消 | Task `running` |
| 完整 | “已确认{游戏名}文件完整” | 继续下一步 | `completed + IntegrityPassed` |
| 文件损坏/缺失 | “{游戏名}文件不完整：发现{数量}项异常” | 查看异常；在有明确支持路径时修复或重新定位后重试 | `completed + IntegrityFailed`；不提升 Game 状态 |
| 缺少/为空/不匹配 manifest | “无法确认{游戏名}文件完整性：缺少可用校验清单” | 获取受支持 manifest、更新来源或稍后重试 | `completed + IntegrityUnsupported`；绝不显示通过 |
| 校验读取失败 | “无法读取{游戏名}文件，完整性校验未完成” | 重新授权或重新选择路径后重试 | Task `failed`；保留上一次可信结果 |

校验成功、文件损坏和 manifest 缺失必须是不同的业务结果。`pkg_version`、`config.ini` 或关键可执行文件存在不能把“缺 manifest”提升为“完整”。网络/API、路径授权和解析错误的重试动作也必须分别说明，不进行没有前置条件变化的无限自动重试。

## 4. Wine 来源、目录与下载状态流

### 4.1 选定来源和目录查询

```text
用户选择官方 GitHub 或预置可信镜像
  ↓
检查来源配置与身份
  ├─ 配置无效 → sourceConfigurationError
  └─ 配置有效 → 查询所选来源 API
       ├─ API 成功且目录有匹配版本 → availableManagedVersions
       ├─ API 成功但目录为空 → noAvailableManagedVersion
       ├─ API 返回 403 → sourceConfigurationError（保留来源身份和 403 事实）
       ├─ API 响应格式/身份不可验证 → catalogInvalid
       └─ API 请求不可达/超时/限流 → networkFailure（保留来源身份）
```

API 失败只说明目录查询没有取得可信响应，不等同于“没有版本”。有效响应但没有条目才是空目录；403 是选定来源拒绝访问，属于来源配置/认证失败，不能显示为空目录或普通网络失败。用户可以在失败后重试同一来源，或主动改选另一个预置来源。不得自动使用 allowlist 外来源或系统 Wine。`networkFailure`、`sourceConfigurationError`、`catalogInvalid`、`downloadFailure` 和 `installationPersistenceFailure` 是错误类别或业务结果，不是新的 Task 状态。

| 来源/结果 | 准确文案 | 恢复动作 | 终态/影响 |
|---|---|---|---|
| 尚未选择来源 | “尚未选择托管 Wine 版本源” | 选择官方 GitHub 或预置可信镜像 | 空状态；不发起请求，不显示版本为空 |
| 查询中 | “正在检查{来源}的托管 Wine 版本” | 等待或取消查询 | 过程态；不能显示空列表 |
| 官方 GitHub API 网络失败（非 403） | “无法连接官方 GitHub 版本源” | 检查网络后重试，或选择预置镜像 | 目录查询失败；不改变已有有效 Wine |
| 预置镜像 API 网络失败（非 403） | “无法连接所选镜像版本源” | 检查网络后重试，或改选官方 GitHub/其他预置镜像 | 目录查询失败；保留所选镜像身份 |
| 官方 GitHub API 返回 403 | “官方 GitHub 版本源拒绝访问（403）” | 稍后重试或选择预置镜像；不要求用户提供 token | `sourceConfigurationError`；不是空目录、不是普通网络失败 |
| 预置镜像 API 返回 403 | “所选镜像版本源拒绝访问（403）” | 稍后重试或改选其他预置来源；不要求用户提供 token | `sourceConfigurationError`；保留镜像身份 |
| API 成功但目录为空 | “所选来源没有可用的托管 Wine 版本” | 稍后重试或选择另一个预置来源 | `noAvailableManagedVersion`；不是网络失败 |
| API 响应不可验证 | “版本源返回的信息无法验证” | 稍后重试；保留诊断信息 | `catalogInvalid`；不能选择该版本 |
| MiPlay 来源配置错误 | “运行环境版本源配置错误” | 更新 MiPlay 或等待修复 | `sourceConfigurationError`；不要求用户改 URL |
| 找到目录 | “找到可用的托管 Wine 版本” | 选择版本并开始下载 | 目录成功，不是 `WineReady` |

“镜像失败”仅在用户选定该镜像并且该镜像请求失败时使用。官方失败不自动变成镜像成功；镜像成功也必须在用户明确选择该镜像后成为当前来源事实。

### 4.2 Artifact 下载、校验和安装

```text
目录版本已选定
  → WineVersionDownload pending：已提交下载，尚未开始
  → running：下载 / 临时文件校验 / 解压 / 安装提交
  ├─ 用户取消且临时内容已清理 → cancelled，未安装
  ├─ API 之后的 asset 无法取得 → failed(downloadFailure)
  ├─ 下载内容或安装状态无法验证 → failed(integrityFailure)
  ├─ 安装或 AppData 写回失败 → failed(installationPersistenceFailure)
  └─ 安装重读、环境准备和验证均通过 → completed + WineReady
```

| 阶段/结果 | 准确文案 | 恢复动作 | 终态定义 |
|---|---|---|---|
| pending | “已提交下载{版本}，等待执行” | 等待或在未开始时取消 | Task `pending`；未发出下载动作 |
| running | “正在下载{版本}，尚未安装完成” | 查看真实阶段；按任务规则取消 | Task `running`；不显示已安装 |
| asset 下载失败 | “下载{版本}失败：未取得完整文件” | 重试同一来源，或主动选择其他预置来源 | Task `failed`；临时/部分文件不得成为已安装版本 |
| 下载被取消 | “下载已取消，未安装{版本}” | 重新选择版本并提交新任务 | Task `cancelled` 仅在清理确认后成立 |
| 内容验证失败 | “下载内容无法验证，未安装{版本}” | 清理不完整内容后重新下载；必要时换预置来源 | Task `failed`；不进入 `WineReady` |
| 安装/持久化失败 | “Wine 已下载但安装状态无法确认” | 重试安装/恢复；在确认前不能启动 | `failed + recoveryRequired`（若已有副作用）或普通 `failed` |
| 完成 | “游戏运行环境已准备好” | 继续目标游戏的前置校验/启动 | Task `completed`，并且托管安装、验证、环境准备和重读均成功 |

API 成功、asset 可达、文件存在、下载进度达到 100%、解压成功和 `wine --version` 输出均不能单独产生 `WineReady`。下载失败必须和 API 失败、镜像 API 失败、内容验证失败分开记录；UX 只表达结果类别和恢复动作，具体下载与校验机制由下游契约负责。

## 5. 六项高级配置的 per-game 状态

六项配置都在每个游戏自己的详情上下文中显示。适用性由发布清单按 Game ID 决定，不因选中某款游戏而套用另一款游戏的规则。

当前已冻结的适用范围事实：A-02 只针对原神；A-03 和 A-06 的目标范围覆盖三款游戏。A-01、A-04、A-05 的逐游戏适用范围在发布清单没有明确前，不得由 UX 推断；对应游戏显示“适用范围未确认/不可用”，而不是显示可应用。

| ID | 名称 | Per-game 归属规则 | 本轮状态 | 用户可见恢复 |
|---|---|---|---|---|
| A-01 | Retina | 由发布清单按 Game ID 确认 | 目标存在但实现 Deferred；未声明适用范围的游戏为不可用 | 查看原因；没有执行或重试动作 |
| A-02 | Steam patch / Steam 白名单启动 | 仅原神适用 | 原神 Deferred；星穹铁道、绝区零不可用 | 原神显示“尚未实现”；其他游戏显示“不适用于此游戏” |
| A-03 | 旧版反作弊文件替换 | 适用范围覆盖三款，但仍需版本/资源检查 | 三款均 Deferred | 查看目标版本/资源不可用原因；不允许应用 |
| A-04 | Metal HUD | 由发布清单按 Game ID 确认 | 目标存在但实现 Deferred；未声明适用范围的游戏为不可用 | 查看原因；没有执行或重试动作 |
| A-05 | 左 Command 映射 Control | 由发布清单按 Game ID 确认 | 目标存在但实现 Deferred；未声明适用范围的游戏为不可用 | 查看原因；没有执行或重试动作 |
| A-06 | hosts 屏蔽 | 适用范围覆盖三款，但仍需真实权限/资源检查 | 三款均 Deferred | 查看权限/实现状态；不允许应用 |

### 5.1 高级配置状态语义

以下是 UI 对 Domain/ViewModel 事实的投影命名，不是新的 Architecture 枚举：

| UX 状态 | 文案 | 是否可执行 | 终态与恢复 |
|---|---|---:|---|
| 空 | “尚未读取此游戏的配置状态” | 否 | 读取该 Game ID 的状态后进入其他状态 |
| 加载中 | “正在检查{选项}对{游戏名}的状态” | 否 | 检查完成前不能显示已启用/已应用 |
| Deferred | “{选项}当前版本尚未实现” | 否 | 结构和状态可查看；没有应用、重试、回滚按钮 |
| 成功（未来真实实现后） | “{选项}已应用并验证” | 是后续版本能力 | 只有真实修改、验证和记录成功后成立；失败仍按失败/回滚处理 |
| 失败 | “{选项}未完成，当前状态未确认/未改变” | 否，直到恢复条件满足 | 在同一 Game ID 详情中查看原因、恢复或回滚结果 |
| 不可用 | “{选项}不适用于此游戏或当前资源/权限不可用” | 否 | 查看具体前置条件；不得创建成功任务 |

Deferred 选项不能被主按钮、Toggle、可提交表单或“已启用”文案伪装。即使用户点开详情，也只显示目标、适用范围和实现状态。

## 6. 兼容性方案和性能选项的恢复位置

兼容方案和性能选项是目标游戏的操作上下文。成功、失败、自动回滚、回滚失败、权限不足和资源不可用都从该游戏详情进入和返回；恢复动作不能被移到全局 Wine 或通用设置，避免用户对错游戏执行操作。

### 6.1 兼容方案

1. 进入某游戏的兼容性方案后，页面标题、状态和所有任务都带目标 Game ID。
2. `Applying` 只显示“正在应用，等待验证”；不能显示“已应用”。
3. 后置验证失败时显示“方案应用未完成，正在恢复应用前状态”。
4. 自动回滚验证成功显示“应用未成功，应用前状态已恢复并确认”，方案终态为 `RolledBack`。
5. 回滚失败或持久化失败显示“方案状态未确认，当前不能重试”，保留 `recoveryRequired`；用户只能执行当前明确的恢复/查看日志动作。
6. 只有真实操作、验证和记录全部成功才显示“方案已应用并验证”；这不表示游戏已经启动。

### 6.2 性能选项

性能选项只属于目标游戏。对当前不在产品范围内的帧率解锁等功能，不创建可完成任务，也不显示为已应用。

- 空：该游戏没有已确认的性能选项记录。
- 加载中：正在读取该游戏的性能选项状态。
- 成功：仅表示该游戏选项的真实状态已读回确认。
- 失败：保留原状态，提示在该游戏上下文重试、重新授权或导出日志。
- 不可用：该游戏、当前版本、权限或资源不支持，不能重试直到前置条件改变。

如果性能选项的应用已经发生外部副作用，恢复和回滚必须回到同一个 Game ID 的详情；若状态无法确认，不能回到全局设置重新执行，也不能由 ViewModel 把它复位成成功或关闭状态。

## 7. 多背景组切换流程

### 7.1 背景组是一个完整单元

一组背景包含同一组的背景图、视频、theme/装饰素材及其版本/来源身份。用户切换的是组，不是分别切换图片、视频和 theme；组内素材不能被不同组混用。

背景组选择按 Game ID 保存。切换原神不会改变星穹铁道或绝区零的当前选择。

### 7.2 选择规则

```text
读取当前游戏的背景组
  ├─ 0 组有效 → unavailable：没有可用背景组
  ├─ 1 组有效 → 直接使用；主界面不显示选择圆点
  └─ 多组有效 → 在主界面上方水平居中显示组选择圆点
       → 用户选择目标组
       → 加载并验证目标组的完整素材
          ├─ 成功：提交目标 Game ID 的选择
          └─ 失败：保留上一有效组并报告目标组不可用
```

- **一组时**：不显示圆点，也不制造“只有一个选项”的交互；组仍有当前选择事实。
- **多组时**：选择圆点水平居中位于主界面上方；每个圆点必须有对应的组名称/版本语义，不能只靠颜色或位置区分。
- **目标组加载中**：保留上一有效组作为当前画面，读出“正在加载{组名}背景组”，不要先清空背景。
- **切换成功**：目标图、视频、theme 全部达到可用门槛后才提交选择并读出“已切换到{组名}背景组”。
- **目标组不可用**：读出“无法使用{组名}背景组，已保留上一组”；恢复为重试目标组或继续使用上一有效组。
- **当前组失效**：进入不可用状态时保留失败原因；若存在其他有效组，可明确建议用户选择其他组，但不得静默切换并假装用户已选择。
- **无任何有效组**：显示“当前没有可用背景组”，主流程仍可使用游戏信息和操作；背景资源失败不得阻断不相关的启动/设置任务。

背景资源的加载状态是媒体事实，不改变 Game 的安装、运行或完整性状态。

### 7.3 背景组状态表

| 状态 | 文案 | 恢复动作 | 终态定义 |
|---|---|---|---|
| 空 | “尚未读取背景组” | 读取当前游戏的背景目录 | 没有当前选择结论 |
| 加载中 | “正在加载{游戏名}背景组” | 等待；可取消时取消加载 | 仍保留上一有效组 |
| 成功 | “当前背景组：{组名}” | 切换其他有效组或继续使用 | 选择已提交并验证 |
| 失败 | “{组名}背景组加载失败” | 重试该组或继续上一组 | 当前选择不改变 |
| 不可用 | “当前没有可用背景组” | 稍后重新获取/读取 | 不阻断其他游戏任务 |

## 8. 键盘、VoiceOver 与动态状态语义

### 8.1 总原则

Accessibility Tree 的 label、role、value、hint、enabled、busy 和 announcement 必须来自 Domain/ViewModel 的结构化状态投影。UI 不得从颜色、hover、Liquid Glass、圆点数量、spinner 或视觉进度条猜测业务状态。

每个动态状态至少包含：目标 Game ID 或来源身份、任务/读取阶段、当前事实、是否可操作、唯一恢复动作和终态。未确认的事实要明确读作“无法确认/当前不能重试”，不能省略成“失败”或“已完成”。

### 8.2 设置和游戏对象

| 对象 | Role / Label | Value / Hint | 动态 announcement |
|---|---|---|---|
| 设置导航 | 互斥选择项；“通用”“Wine 运行环境”“原神”等 | 当前选中层级和该层状态 | “已进入{层级}设置；目标为{Game ID/全局}” |
| Game 入口 | 可激活选择项；“切换到{中文名} / {English name}” | 选中状态、业务状态、当前可用动作 | 切换后读出目标游戏和当前状态 |
| 原始 metadata 行 | 静态文本/可复制值；“{section} {key}” | 原始 value、来源、读取时间、可确认性 | 读取完成或失败时说明来源和失败类别 |
| Wine 来源选择 | 选择控件；“Wine 来源” | 官方 GitHub 或预置镜像名称、连接/目录状态 | 来源改变时读出“已选择{来源}，等待检查” |
| 版本目录 | 列表项；“托管 Wine {version}” | 架构、来源、已安装/可下载，不把目录读作就绪 | 目录成功、空目录、API 失败分别播报 |
| 高级配置 | 非可执行状态行；“{选项}，{游戏名}” | Deferred/不可用/已验证状态和原因 | Deferred 必须读出“当前版本尚未实现，不可执行” |
| 背景组 | 选择项；“{组名}背景组” | 当前选中、可用/加载中/失败、组版本 | 选择成功或失败时读出保留上一组的事实 |

### 8.3 键盘行为

- 设置导航、来源、版本和当前游戏的可操作对象按稳定的阅读顺序进入键盘焦点；切换游戏后焦点留在对应 Game ID 的同一语义位置。
- 选择背景组时，方向键只在有效组之间移动，Return/Space 提交选择；一组有效时没有圆点选择对象，也没有无意义的单项焦点。
- `pending` 任务在未开始时可用取消；`running` 是否可取消由任务事实决定。取消只发送取消意图，不能把“已请求取消”读成已取消。
- 任务已开始不可取消或正在回滚时，取消控件应不可用并读出“恢复正在进行，必须完成验证”。
- Return/Space 激活重试、重新授权或选择路径时，调用与鼠标和 VoiceOver 相同的用户意图；不产生旁路业务逻辑。
- Escape 只关闭当前可取消的临时读取/选择流程，不撤销已经发生的外部修改；有未确认副作用时必须先完成恢复。
- `⌘,` 进入/聚焦设置窗口；进入后焦点落在当前设置层的标题和状态，不让主窗口控件继续参与当前键盘路径。

### 8.4 动态状态播报模板

| 状态 | 必须读出的内容 |
|---|---|
| pending | “{目标}已提交，等待执行；尚未{成功动作}” |
| running | “正在{目标}{阶段}；{真实进度或进度未知}；{可否取消}” |
| completed | “{目标}已完成：{独立业务结果}；{下一步}” |
| failed | “{目标}未完成：{具体原因}；{是否改变目标}；下一步：{唯一恢复动作}” |
| cancelled | “{目标}已取消，清理/回滚已确认；目标保持{原状态}” |
| recoveryRequired | “{目标}状态未确认，当前不能重试；下一步：{恢复动作}” |
| unavailable | “{目标}当前不可用：{前置条件}；改变条件后才能继续” |

真实进度不可得时读“进度未知”，不根据耗时或视觉条估算。来源目录空、API 失败、镜像失败、下载失败和校验失败必须分别播报其事实；“加载失败”不作为统一替代文案。

## 9. P0/P1 失败语义连续性

本次修订不重写已有的任务契约，但以下 P0/P1 语义继续适用于新设置和游戏详情流程：

| 失败事实 | 准确文案 | 恢复动作 | 终态定义 |
|---|---|---|---|
| Wine 未就绪 | “游戏运行环境未准备好，游戏尚未启动” | 进入 Wine 设置，选择批准来源/版本并完成验证 | 启动任务 `failed`；Game 不进入 `Running` |
| 进程启动失败 | “游戏进程未能启动” | 查看阶段和错误；修复前置条件后重试 | Task `failed`，Game `LaunchFailed` |
| 进程启动超时 | “等待游戏启动超时，正在确认并清理残留” | 等待 termination/清理确认；确认后才可重试 | 未确认时 `failed + recoveryRequired`；不得显示 `Running` |
| 进程异常退出 | “游戏进程异常退出，游戏未保持运行” | 查看退出事实、日志或目标游戏兼容性方案 | Task/session `failed`，Game `LaunchFailed`；不把短暂进程存在当成功 |
| sandbox/bookmark stale | “正在刷新{游戏名}路径授权” | 在有效授权范围内写回刷新结果；失败则重新选择路径 | 写回和重读前不发布校验、版本或启动成功 |
| 权限拒绝 | “无法访问{游戏名}路径：需要重新授权” | 重新授权或重新选择可执行文件路径 | Task `failed`；原路径/业务状态不被伪装为已接入 |
| AppData 损坏 | “应用数据无法读取，已有备份可用于恢复” | 验证备份后恢复；无备份时明确重新开始 | 恢复重读验证前，不能确认路径、语言、Wine 选择或历史 |
| 恢复/迁移写回失败 | “应用数据恢复未完成，当前不能继续” | 保留原文件和备份，重试恢复或明确重新开始 | `failed + recoveryRequired`；不自动用默认值替代 |

进程退出事实写入失败时，重启边界仍优先显示恢复保护，不将持久 `Running` 当作真实运行；stale bookmark 刷新写回失败时，也不把本次读取结果升级为成功。所有恢复动作仍回到目标 Game ID 或明确的通用 AppData 上下文。

## 10. 用户反馈逐条核对矩阵

| 反馈/需求 | 本稿覆盖位置 | 验收事实 |
|---|---|---|
| 设置页层级混乱 | §2 | 通用、Wine、三款 Game ID 独立入口；无跨游戏继承 |
| 中英文名称及 metadata 字段 | §3.1 | 同一语义行显示名称；明确 `game_version`、`channel`、`cps`、`sub_channel`、`config.ini` 和来源 |

| 没有可用版本被误报为网络失败 | §4.1 | 空目录为 `noAvailableManagedVersion`，不等于 API 失败 |
| 下载完成被误报为安装成功 | §4.2 | 下载、校验、安装、持久化和 `WineReady` 分层 |
| 六项高级配置伪装可执行 | §5 | A-01 至 A-06 的 per-game Deferred/不可用/未来成功语义明确，无执行动作 |
| 兼容性和性能失败后找不到恢复 | §6 | 恢复留在目标 Game ID 详情上下文，不移动到全局设置 |
| 一组背景仍显示圆点 | §7.2 | 一组不显示圆点 |
| 多组背景位置和切换不完整 | §7.2 | 多组圆点位于主界面上方水平居中；加载失败保留上一有效组 |
| VoiceOver 依赖视觉元素 | §8 | Accessibility Tree 由 Domain/ViewModel 状态投影提供完整语义 |
| 键盘无法完成错误恢复 | §8.3 | 重试、授权、取消、背景切换和设置入口有明确键盘动作 |

本稿不把任何 Deferred 功能提升为当前可执行任务，不修改 Architecture 的状态集合，也不改变 Product 已冻结的游戏、Wine 来源或数据字段边界。

## 11. 与 Product / Architecture 的核对结论

| 约束 | UX 核对结果 |
|---|---|
| Product：MiPlay 托管 Wine、官方 GitHub 与预置镜像 | §2.2、§4 允许两类选定来源；禁止任意 URL 和系统 Wine；API、镜像、下载、校验和安装状态分开 |
| Product：原始 `config.ini` 和已确认 metadata | §3 保留原始 key/value、来源和读取时间；不把 `pkg_version` 或 `config.ini` 越权为完整性结论 |
| Product：按 Game ID 独立设置和背景组 | §2.3、§7 规定三款独立保存、异步结果按原目标归属、目标组失败保留上一有效组 |
| Product：六项高级配置可 Deferred | §5 对 A-01 至 A-06 逐项给出 per-game 状态；Deferred 无执行动作、无成功任务、无已应用文案 |
| Architecture：TaskScheduler 状态集合不扩展 | §1、§8 使用 `pending/running/completed/failed/cancelled`；`recoveryRequired` 只作为恢复保护事实 |
| Architecture：UI → ViewModel → Domain → Infrastructure | §8 要求 AccessibilityProjection 来自 Domain/ViewModel 结构化事实；UI 不从视觉元素推断状态 |
| Architecture：成功事件必须在持久化和后置验证后发布 | §1、§4、§6、§7 将安装、方案、背景组和取消的提交/重读验证写入成功门槛 |

因此，本次 UX 修订不新增业务能力，不替 Product 决定未冻结的高级配置适用范围，也不把视觉呈现当作状态事实源；下游 UI 和 Implementation 应以本稿的文案、恢复动作和终态定义为唯一交互解释。
