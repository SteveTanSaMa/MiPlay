# MiPlay UX 设计原则

> **文档状态**：活跃（Active）
> **UX 阶段**：UX Principles
> **更新日期**：2026-08-03
> **继承自**：Product Vision、Product Features、Product Domain、Research UX Patterns、Research Design Principles

## 1. 结果先于请求

- **原则**：用户发起操作、操作进入队列、执行请求发出、外部动作完成、后置验证通过是五个不同事实。任何较早事实都不能替代成功结果。
- **适用**：游戏启动、兼容方案应用、完整性校验、版本检测、路径定位和数据恢复。
- **必须遵守**：`pending` 只能表达已接受但尚未执行；`running` 只能表达正在执行；只有满足该任务的成功门槛后才可使用成功文案或 `completed`。
- **Trade-off**：状态数量和反馈内容增加，用户需要等待最终确认；换取的是不把未执行或未验证的动作误报为已完成。

## 2. 每个失败都提供下一步

- **原则**：失败反馈必须同时说明失败对象、失败阶段、当前是否改变了目标状态、用户可执行的恢复动作和不可再继续的条件。
- **适用**：P0/P1 所有失败路径，尤其是权限、进程、校验、回滚和持久化失败。
- **必须遵守**：没有恢复动作时不得显示伪装成可操作的成功入口；不适合重试时明确说明等待外部条件或重新选择路径。
- **Trade-off**：错误信息会比单行“失败”更长；换取的是用户可以在 MiPlay 内完成有依据的恢复，而不是重复盲点。

## 3. 破坏性动作必须有可验证的回路

- **原则**：涉及系统配置或游戏状态的动作必须按“应用前快照 → 执行 → 后置验证 → 记录结果”闭环。备份完成、命令返回或日志写入都不是应用成功。
- **适用**：当前发布清单中的 CS-01 `modify_hostname` 和 CS-02 `block_network_anticheat`，以及它们的回滚。
- **必须遵守**：验证失败时自动回滚；只有回滚后的状态读回与快照一致才可标记 `RolledBack`。回滚未确认时保留失败事实并阻止继续应用同一方案。
- **Trade-off**：一次操作可能经历更长的等待；换取的是系统状态可解释、可恢复，避免留下未记录的部分修改。

## 4. 任务状态与业务状态分离

- **原则**：TaskScheduler 的 `pending/running/completed/failed/cancelled` 描述任务生命周期；Game、SolutionApplication、IntegrityCheckResult 等业务状态描述目标对象结果，两者不可互换。
- **适用**：所有队列任务和跨模块状态同步。
- **必须遵守**：任务 `completed` 只能表示获得了该任务定义的可信终局结果；业务结果可能是“完整”“损坏”或“无可用清单”等不同值。任务 `failed` 必须表示没有达到请求目标或无法获得可信结果。
- **Trade-off**：调用方需要同时读取任务状态和结果；换取 UI、ViewModel、Domain 不会因一个“完成”词而各自推断不同含义。

## 5. 终态必须可行动且可解释

- **原则**：每个终态都要明确是否可重试、是否需要重新授权、是否需要重新选择路径、是否可以关闭流程，以及目标对象最终处于什么状态。
- **适用**：启动失败、运行环境失败、完整性损坏、版本检测失败、兼容方案不可用和 AppData 恢复结果。
- **必须遵守**：成功、已回滚、已取消、失败、不可用不能共用同一文案；错误终态不得把目标对象提升为“已就绪”。
- **Trade-off**：文案和状态映射需要持续维护；换取用户可预测地决定下一步。

## 6. 恢复动作不隐瞒外部条件

- **原则**：重试不是万能恢复。网络不可用、权限被拒绝、路径授权失效、manifest 不支持、进程残留和数据损坏必须分别说明需要用户或系统先改变的条件。
- **适用**：版本检测、运行环境准备、路径访问、兼容方案应用和 AppData 恢复。
- **必须遵守**：有限重试结束后停止自动循环；没有改变前置条件时，重复执行同一动作不能被包装成新的成功尝试。
- **Trade-off**：某些失败需要用户离开当前操作去修复网络或授权；换取的是避免无穷重试和资源浪费。

## 7. Wine 技术对用户隐形，事实对用户透明

- **原则**：用户不需要理解 Wine、prefix 或运行时构建；但必须知道“运行环境正在准备”“准备失败会阻止启动”“可通过重试恢复”等与任务相关的事实。
- **适用**：首次启动、兼容方案依赖的运行环境准备、运行环境失效后的恢复。
- **必须遵守**：面向用户的主文案使用“运行环境”或“游戏运行环境”，技术名称只在日志或面向排障的详细信息中出现；运行环境未就绪时不得显示“启动成功”。
- **Trade-off**：高级用户在主流程中得到的技术细节较少；换取普通玩家无需学习实现机制也能作出正确决策。

## 统一文案规则

以下规则适用于六份 UX 交付文档中所有状态：

| 不准确的说法 | 准确说法 |
|-------------|---------|
| 已完成（用户刚点击操作） | 已提交，等待执行 |
| 已应用（刚备份或命令已发出） | 正在应用，等待验证 |
| 启动成功（进程已创建） | 正在启动，等待进程确认 |
| 校验通过（只检查到可执行文件） | 已找到文件，正在等待完整 manifest 校验 |
| 已恢复（只读到备份文件） | 正在恢复，等待恢复后读回验证 |
| 可用（有静态方案定义） | 当前资源、适用范围和权限均满足，可应用 |

## P1 Issue 补充约束

以下是对既有七条原则的状态约束补充，不新增业务状态或任务状态：

1. **运行时来源事实**：只有 MiPlay 托管、来源在 allowlist 内、完成安装提交和前置验证的版本才可进入 `WineReady`。MiPlay 不检测系统 Wine、Whisky 或 CrossOver，也不提供选择、导入、回退使用或无障碍展示这些运行时的路径。
2. **版本源错误分层**：版本源查询必须让用户区分“没有可用版本”“网络失败”“版本源配置错误”和“下载中”。合法空目录不是网络失败；下载阶段不是版本列表为空；镜像成功也不能把远程条目直接说成已安装或已就绪。
3. **本地证据不越权**：`pkg_version` 可以成为经格式和目标关联验证后的本地版本候选；`config.ini` 可以成为渠道/来源元数据候选。二者都不能替代非空、版本对应且全条目通过的 manifest，也不能单独产生 `IntegrityPassed`、`current` 或 `WineReady`。
4. **恢复先于新结果**：重启发现持久 `Running` 但没有可信活动进程，或 stale bookmark 刷新写回未验证时，必须保留 `recoveryRequired` 事实；不得发布 `Installed`、`Running`、`IntegrityPassed`、`current` 或新的启动重试入口。
5. **无障碍读取事实**：游戏卡片、任务进度、错误和恢复动作的 Accessibility label/value/hint/role 来自 Domain/ViewModel 状态投影。颜色、透明度、hover、Liquid Glass 层次和视觉进度条都不能单独承载业务事实。
